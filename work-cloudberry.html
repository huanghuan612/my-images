Case Study

Cloudberry

复杂数据库任务的清晰工作台
Cloudberry 是一款面向数据分析师和数据库用户的 Web 工作台，支持 SQL 编写、执行与结果查看。我的工作重点不是增加更多功能，而是梳理专业用户高频使用的工作路径，让复杂操作更连续、更容易掌控。

The Challenge

专业工具不是功能少，而是信息太多

数据库用户需要同时处理工作表、数据库资源、SQL 代码、执行状态和查询结果。界面上的每一个面板都有存在的理由，但当它们同时出现时，用户的认知负荷会迅速超载。

真正的问题不是某个按钮不好用，而是任务容易中断。用户需要不断确认：我现在在哪？SQL 运行到哪里了？结果出来了吗？我要不要切到别的页面？

核心设计问题：如何让用户在复杂数据库任务中，始终保持上下文连续？

Design Principle

一个工作空间，一条连续任务

我把整个体验围绕一条核心任务重新组织。尽量减少页面跳转，让用户在同一个工作空间里完成主要任务。

01

Context over navigation

尽量让任务发生在同一个工作空间，而不是增加页面跳转。

02

Feedback over speed

数据库任务未必能更快，但可以让等待更明确。

03

Assistance over memory

让系统在输入过程中提供帮助，而不是依赖用户记住所有知识。

04

Flow over features

功能不是孤立存在，而是围绕完整任务链组织。

我的角色

UX / Product Design

  • 信息架构重组，定义 Worksheet 为核心的任务模型
  • 交互流程设计，减少页面跳转与上下文丢失

更清晰的任务组织

Worksheet 与 Database 保持稳定可见，用户始终知道自己身在何处。

cloudberry.app/worksheets

设计决策

将数据库资源树与 Worksheet 编辑器并置在同一视图，用户无需在"找表"和"写 SQL"之间来回切换。左侧导航保持固定，右侧编辑区随 Worksheet 切换而更新。

关键特性

  • 侧边栏数据库资源树，支持折叠与搜索
  • Worksheet 标签页管理，多任务并行不丢失上下文
  • 表结构悬停预览，减少跳转查看表定义的次数

更连续的 SQL 编辑

自动补全与文档信息减少操作中断，让编写过程保持心流。

cloudberry.app/worksheet

设计决策

SQL 编辑器不是简单的文本框，而是理解上下文的智能界面。自动补全不仅提示关键字，更根据当前数据库的表结构提供精准建议，让用户无需记忆所有字段名。右侧 Docs 链接随时可查，不打断编码节奏。

关键特性

  • 上下文感知的 SQL 自动补全
  • 表/字段文档悬停提示
  • 语法高亮与实时错误检查
  • 查询历史与快速复用

从执行到结果的完整闭环

执行过程始终可感知、可控制；结果与编辑器同屏呈现，验证无需跳转。

cloudberry.app/worksheet — executing
执行中 — 实时进度与取消控制
cloudberry.app/worksheet — results
执行完成 — 结果表格与编辑器同屏

设计决策

执行状态不是简单的"加载中"，而是展示真实的执行进度。用户可以看到查询进行到哪一步、已运行多久、扫描了多少数据，同时提供 Cancel 按钮让用户始终保有控制权。执行完成后，结果区域自动展开，与编辑器上下排列，目光只需向下移动即可验证结果，无需离开当前页面。

关键特性

  • 实时执行进度与阶段提示（9/111 查询进度、已运行时间）
  • 执行详情展示：Start Time、ID、Warehouse、Produced Rows
  • 一键取消执行，安全回退
  • 编辑器与结果区同屏展示，无需跳转
  • 结果表格支持 Find/Replace 快速定位数据
  • 表头固定、行号对齐、数据类型一目了然
Outcome

让复杂工作更容易掌控

Cloudberry 最终形成了一套围绕核心工作流展开的数据库工作台：

更清晰的任务组织

Worksheet 与 Database 保持稳定可见。

更连续的 SQL 编辑

自动补全与文档信息减少操作中断。

更明确的执行反馈

长时间查询过程始终可感知、可控制。

更短的验证闭环

从代码编辑到结果查看保持在同一上下文中。

不是把数据库工作变简单，而是让复杂工作更容易掌控。

"专业用户不怕复杂，他们怕失去上下文。"
在高复杂度工具里，好的体验不是减少所有信息，而是让信息在正确的时间、正确的位置出现。
